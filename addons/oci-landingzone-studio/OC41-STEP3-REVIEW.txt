Identity-domain findings
------------------------
1. The inspected Du tenancy has an ACTIVE Default identity domain in PCZ.
   Its OCID was not provided in the saved profile and is not stored here.
2. gen/builders/iam/identity_domains.libsonnet always emits a new COMMON-DOMAIN
   definition named id_lz_common, with license type free, and directs base groups
   to COMMON-DOMAIN. This differs from using the existing Default domain.
3. gen/builders/iam/context.libsonnet hardcodes id_lz_common as the group-policy
   qualifier. Base tenancy/project policies and RPC requester references consume
   that context.
4. ExaDB IAM hardcodes the same display name independently in
   gen/workload-extensions/exadb/iam.libsonnet. Its group definitions contribute
   through identity_domain_groups_configuration.
5. OKE and OCVS IAM also hardcode id_lz_common. Their groups are emitted through
   groups_configuration, handled by the legacy oci_identity_group module rather
   than the SCIM identity-domain group path. The groups' actual domain and the
   policy qualifier must be checked together; changing only base IAM cannot
   establish consistent workload identity behavior. This is a source-level
   consistency concern, not a claim that an existing deployment was tested.
6. Some standalone Exadata publication adapters explicitly bind COMMON-DOMAIN.
   Keep their existing publication contract intact; do not accidentally change
   published profiles while adding a config-mode option.
7. FoundationConfig and LzConfig currently have no identity-domain selection.
   A generator-only option would also need later Studio model, input,
   serialization, import, saved-design and review support to be usable in Studio.

Existing-domain deployment contract
-----------------------------------
The pinned IAM module supports existing domains without creating a domain:
- identity-domains/main.tf creates domains only from the entries in
  identity_domains_configuration.identity_domains; null configuration creates
  no domain through that resource.
- identity-domains/groups.tf resolves a literal domain OCID, or a dependency key,
  then reads its URL with data.oci_identity_domain.grp_domain and uses that URL
  for SCIM group operations.
- A domain display name alone is not accepted as a lookup selector by this path.
- Orchestrator iam.tf forwards the default group domain ID and supports the
  identity_domains_dependency map. rms-facade/get_dependencies.tf recognizes the
  identity_domains family in dependency input files.

Therefore, a literal existing-domain OCID can use the current Orchestrator
contract. An Orchestrator source change is not shown to be necessary for this
path. The browser must not receive signing keys or authenticated CLI access;
the operator supplies deployment metadata privately and authenticates outside
Studio as before. A domain OCID identifies the domain; it grants no access.

Proposed identity behavior for separate approval
------------------------------------------------
- Add an explicit, optional config-mode choice to use the existing Default
  domain. Retain the existing id_lz_common creation behavior when omitted.
  Do not infer domain IDs from realm, tenancy OCID, user OCID or fingerprint.
- Require the real domain OCID for existing mode. Validate its resource type
  and selected realm at the input boundary. Default is the intended display
  name; arbitrary custom existing domains are outside the first scoped change.
- Existing mode must emit no new domain definition and no domain-replication
  resource request. It may create the explicitly requested landing-zone groups
  within Default; it must not adopt existing groups or change memberships
  implicitly. Check conflicting group names before a deployment.
- Base IAM and supported workload policies must consistently qualify the chosen
  domain. Pass normalized identity context to builders; do not replace strings
  in generated JSON or edit published snapshots.
- Exercise OKE, OCVS, ExaDB-D and ExaDB-C@C policy/group consistency where those
  extensions support the selected configuration. Unsupported combinations must
  fail clearly rather than silently creating groups in another domain.
- Keep OC1/OC19 defaults, published profiles and existing group-membership
  management behavior unchanged. This is for new deployment configuration,
  not migration of an already managed id_lz_common domain or groups.

Cloud Guard findings
--------------------
Read-only PCZ calls found one tenancy-root COMPARTMENT target and the Oracle
configuration, activity and threat detector recipes plus the Oracle responder
recipe. Counts and recipe categories are recorded without customer target names,
target OCIDs, tenancy identifiers or private recipe names.

The pinned Security module:
- Creates the Cloud Guard enablement resource only when the service is DISABLED.
- Uses ignore_existing_targets=true by default. An existing target with a
  different name from the requested one is excluded; a matching name may remain
  in the resource map. Name equality does not establish Terraform ownership.
- Determines recipe cloning from the remaining target requests. An existing
  ignored root target does not automatically receive Studio's requested cloned
  recipes, so ENABLED alone is not proof that those settings were applied.
- Looks up exact Oracle detector/responder recipe names. Those names are present
  in the inspected PCZ catalog; cloning permissions and execution are untested.

Recommendation: retain Cloud Guard generation. Add explicit deployment-handover
guidance to inspect the existing target's coverage, recipes and Terraform state.
Do not disable, delete, import or replace it automatically. Do not describe an
ignored target as newly provisioned by this stack. Reconcile recipe ownership
only through a separately reviewed deployment action if necessary.

Do not add arbitrary per-service switches merely because evidence is incomplete.
